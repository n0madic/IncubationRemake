# `tools/exports/` — committed PE export listings

Generated by [`tools/pe_exports.py`](../pe_exports.py) from the retail
binaries in `gog_incubation/`; verified against them by
`pe_exports.py --check gog_incubation`.  Do not edit by hand.

**Scope: only the six original Blue Byte libraries whose exports are useful
surface.**  Everything else under the game root is deliberately excluded as
plumbing a Wine harness would never call by name:

| Excluded | Why |
|---|---|
| `ENGWLIB.DLL` | Blue Byte's platform shim, but nothing observable: 15 `Win_*` file-I/O and memory wrappers the engine calls internally — no oracle for a remake |
| `audio.dll`, `sound.dll` | `winmm.dll` shims — 186 of their 192 exports are forwarders, the remaining six are `aux*/mci*` wrappers |
| `glide*.dll`, `3DfxSpl*.dll` | nGlide / 3Dfx splash wrappers, GOG-era, not Blue Byte code |
| `audiere.dll`, `libogg-0.dll`, `libvorbis*-*.dll` | GOG's CD-audio replacement layer |
| `MSVCRT.DLL`, `msvcirt.dll`, `goggame.dll` | CRT and GOG launcher machinery |
| every `.exe` | no export directory at all — game logic is reachable only at internal addresses (`tools/trace_names.py`) |

* `<binary>.lst` — canonical listing: ordinal, RVA, name, forwarder string,
  plus the image's own header facts (machine, timestamp, internal DLL name).
  Byte-compared against the binaries on every `--check`, so any drift between
  this directory and the game install fails the check.

Names are stored **verbatim**, i.e. still MSVC-mangled for the C++ DLLs:
nothing in this repository can demangle MSVC names (no suitable cxxfilt is
installed and third-party dependencies are out).  The interesting ones,
translated: `NewToolsR.dll` / `aWin.dll` export Blue Byte's utility classes —
`BB::RndGenBase` with `LinearCongruentialRndGen` (`SetSeed(unsigned)`,
`GetRndNr()`, `GetRndNr(unsigned)`), `AdditiveCongruentialRndGen` (same
interface) and `CongruentialRndGen`, the global `BB::Random(unsigned)`;
plus `BBDynArrayBase`, `DListBase`/`SListBase`, `String` and the error
management family.  `BGLWin*.dll` export only the `CBGL*` dialog framework
(`CBGLApp`, `CBGLWindow`, `CBGLDialog`, `CBGLDIBButton`, …) — original Blue
Byte GUI code, no raw Win32 entry points.

## What these listings establish

* Every shipped `.exe` has an **empty export directory** — game logic
  (combat resolution, the AI turn, the save/load chains, the LCL interpreter)
  is reachable only at internal addresses (see `tools/trace_names.py`).
* All directly callable engine entry points are in `Eng3d.dll`
  (`_E3D_*`: collision, software rasterizer, fixed-point math, VISN decode) —
  this is the surface `tools/wine_visn/` already calls under Wine.
* `ENG3DFX.DLL` is the same export set minus `_E3D_get_engine_version`
  (the 3Dfx/Glide build of the engine).
* `aWin.dll` carries the internal name `NewToolsD.dll` — it is a debug-build
  sibling of `NewToolsR.dll`; both export Blue Byte's utility classes
  (`BB::RndGenBase` family RNGs, containers, `String`, error management).
* `audio.dll` / `sound.dll` are `winmm.dll` shims: 186 of their 192 exports
  are forwarders.
* The Glide wrappers (`glide*.dll`), `3DfxSpl*.dll`, `audiere.dll`,
  `libogg/vorbis*` and the CRT DLLs are third-party surfaces, listed here only
  for completeness.

Regenerate with:

```sh
python3 tools/pe_exports.py --write gog_incubation
python3 tools/pe_exports.py --check gog_incubation   # must exit 0
```
